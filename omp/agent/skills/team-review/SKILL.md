# チームレビュー

観点1つにつき担当1人。固定点と差分コマンドを一度だけ決め、観点を並列で走らせ、結果は観点ごとに並べる。観点をまたいで指摘を混ぜたり順位を付け直したりしない。

## 固定点と資料
1. ユーザーが指定した ref を固定点とする。指定がなければ尋ねる。
2. `git rev-parse <固定点>` と `git rev-parse HEAD` を記録する。差分コマンドを `git diff <固定点>...HEAD` に確定し、一度実行して全差分を共有する。`git log <固定点>..HEAD --oneline` も記録する。ref が無効・差分が空ならレビューを止める。未コミットの変更を含める依頼なら HEAD に対する作業ツリー差分も別途共有し、HEAD の通過記録には含めない。
3. `code-review` のステップ2・3に従って、スペックと規約の資料を探す。Spec の根拠が見つからなければ所在を尋ね、存在しないと確認できた場合だけ Spec を外す。

## 名簿

全員を omp の `task` ツールの**同じ呼び出し**で並列起動する。各 task に固定点、差分コマンド全文、共有差分、コミット一覧、対応する資料のパスを渡す。差分が長ければ同じ `artifact://` の出力を全員に渡し、途中で固定点を取り直さない。各担当は自分の観点だけを読み取り専用で検査する。

| 観点 | agent | 外すとき |
| --- | --- | --- |
| Standards（規約とコードスメル） | `review-standards` | なし |
| Spec（イシュー・スペック） | `review-spec` | スペックが存在しないと確認できたとき |
| 定義順 | `review-definition-order` | 関数の追加・移動がないとき |
| 命名の品詞 | `review-naming` | 新しい識別子がないとき |
| 記述の役割分担 | `review-writing-roles` | コメント・テスト・コミットログに変更がないとき |
| 簡潔さ・重複・抽象の高さ | `review-simplicity` | なし |
| セキュリティ | `security-reviewer` | なし |

セキュリティ担当には `~/.agents/skills/security-audit/SKILL.md` を参考資料として**guidance mode**で読ませる。対象は共有した PR 差分と、その信頼境界を確認するために必要な周辺コードだけ。全体監査の六段階・成果物は実行しない。レビューで修正は適用しない。

各担当への共通指示: 「担当観点だけをレビューする。他の観点と混ぜない。各指摘で該当ハンクと根拠を示し、ハードな違反（仕様・明文化された規約・具体的なセキュリティ欠陥）と判断の問題を区別する。ツールがすでに強制する問題は省く。変更しない。報告は日本語で書く。ハード違反件数を明記する」。security-reviewer にも同じ制限と guidance mode を明記する。

## 結果と通過記録

各観点をそれぞれの見出しの下にそのまま、または軽く整えて並べる。各観点の件数とその観点内の最悪の問題を最後に一行で示す。担当が省略された観点は理由を明記し、セキュリティ担当が未実行なら通過扱いにしない。

**ハードな違反が1件も残っていない**ときだけ `verdict: "pass"`。残っているときは `"fail"` とし、未完了・結果不明なら通過記録を作らない。通過時に `git rev-parse --git-path omp-review` が返すディレクトリを作り、`<HEAD の完全な SHA>.json` に JSON を保存する。JSON には `verdict`, `head`, `base`（固定点の ref と解決した SHA）、`perspectives`（観点ごとの結果・ハード違反件数・省略理由）、`reviewedAt`（ISO 8601 日時）を入れる。`security-reviewer` の結果に security-audit guidance mode の実施を明記する。記録は Git 管理下のファイルとして追加しない。HEAD がレビュー中に動いたら記録せず再レビューする。修正後も必ず新しい HEAD で再レビューする。
